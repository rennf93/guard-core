# SecurityConfig Reference

`SecurityConfig` is the single Pydantic model controlling all behavior. The installed model is the source of truth; introspect it for the exact field list, types, defaults, and descriptions.

```python
python -c "from guard_core.models import SecurityConfig; \
import json; print(json.dumps({f: {'default': SecurityConfig.model_fields[f].default, 'description': SecurityConfig.model_fields[f].description} for f in SecurityConfig.model_fields}, indent=2, default=str))"
```

## Grouped surface

Field names below are verified against the installed `SecurityConfig.model_fields`; a per-route knob (set through a decorator, not `SecurityConfig`) is called out explicitly where one could be confused for a global field of the same shape.

### IP / geo

`whitelist`, `blacklist` (IPs/CIDRs; an explicit whitelist match overrides the blacklist), `blocked_countries`, `whitelist_countries` (ISO 3166-1 alpha-2; a non-empty set is restrictive -- only listed countries pass, and an unresolved country is blocked), `block_cloud_providers` (`frozenset[str] | None`; six providers -- `AWS`, `GCP`, `Azure`, `DigitalOcean`, `Linode`, `Vultr`; bare `"GCP"` blocks the whole provider, `"GCP:!us-central1"` carves out a region, region data exists for AWS/GCP only so a carve-out on the other four exempts nothing; an unrecognized provider name raises `ValueError` at construction and reassignment instead of being silently dropped), `geo_ip_handler` (`GeoIPHandler | None`), `ipinfo_token`/`ipinfo_db_path` (deprecated, create a custom `geo_ip_handler` instead), `trusted_proxies` (also accepts the literal `"unix"` token alongside IPs/CIDRs, marking a peer-less connection -- e.g. a Unix-socket deployment -- as a trusted hop so `X-Forwarded-For` still resolves the real client through `extract_client_ip`; `guard_core/_utils/ip_extraction.py`), `trusted_proxy_depth` (default `1`), `trust_x_forwarded_proto`.

`IPInfoManager`, the default `geo_ip_handler` built from `ipinfo_token`, keeps the last known good GeoIP database and reader on a failed refresh or download: `refresh()` does not clear `self.reader` before attempting a download, and neither `initialize()` nor `refresh()` deletes the on-disk `.mmdb` file when a download fails, so country lookups keep working off the prior database (`guard_core/handlers/ipinfo_handler.py`, `initialize` and `refresh`). Only a database that fails to open (a corrupt file) is discarded, via `_open_database_or_none` (`guard_core/handlers/ipinfo_handler.py:87-96`). Every download writes to a temporary file and swaps it in atomically with `os.replace` (`_write_database_atomically`, `guard_core/handlers/ipinfo_handler.py:103-112`).

Azure cloud-IP fetch (`block_cloud_providers` including `"Azure"`) loads the `AzureCloud` service tag by name from the Microsoft ServiceTags document, instead of whichever tag the document happens to list first (`_AZURE_CLOUD_SERVICE_TAG_NAME`, `guard_core/handlers/_cloud_azure_fetch.py:28`).

When `request.client_host` is `None` (no connecting-peer address), the resolved identity is `"unknown"` (`UNKNOWN_CLIENT_IDENTITY`) unless `"unix"` is in `trusted_proxies` and an `X-Forwarded-For` chain resolves a real client. An `"unknown"` identity passes the global and route-level IP/country checks unless a global `whitelist`, `whitelist_countries`, a route `ip_whitelist`, or a route `whitelist_countries` is configured, in which case it is blocked (`guard_core/_utils/access_control.py`, `guard_core/core/checks/helpers.py`).

Route-level IP/country overrides (`ip_whitelist`, `ip_blacklist`, `blocked_countries`, `whitelist_countries`, `require_https`) live on `RouteConfig`, set via decorators, not on `SecurityConfig`.

### Rate limiting / bans

`rate_limit` (default `10`), `rate_limit_window` (default `60`), `auto_ban_threshold` (default `10`, `ge=1`), `auto_ban_duration` (default `3600`, `ge=1`), `threat_ban_config` (`MappingProxyType[str, ThreatBanConfig]`, a read-only mapping; per-category threshold/duration override, unlisted categories fall back to `auto_ban_threshold`/`auto_ban_duration`; categories are the detection categories plus the pseudo-category `"rate_limit"`), `enable_rate_limit_auto_ban` (default `False`; feeds active-mode rate-limit violations into the same auto-ban engine penetration detection uses, keyed under the `"rate_limit"` pseudo-category; requires `enable_ip_banning` to actually ban), `global_behavior_rules` (`tuple[BehaviorRuleConfig, ...]`, applied to every route in addition to any decorator-specified rules; immutable -- reassign the whole field rather than `.append()`), `behavior_scan_response_body` (default `False`; opt-in gate for `return_pattern` behavior rules that read the response body -- `json:`, `regex:`, or a bare substring; `status:` patterns are unaffected), `behavior_max_response_body_inspect_bytes` (default `262144`, range `1024`-`10485760`; leading-prefix cap on what guard-core reads and retains from a response body for `return_pattern` inspection), `enable_ip_banning` (default `True`), `enable_rate_limiting` (default `True`), `endpoint_rate_limits` (per-endpoint limits, normally set by dynamic rules).

Per-route rate limiting (`rate_limit`, `rate_limit_window`, `geo_rate_limits`) and per-route `behavior_rules` live on `RouteConfig`.

In-memory rate-limit stores (`RateLimitManager.request_timestamps` and the module-level `_by_ip_request_timestamps`/`_by_ip_autoban_counts` in `guard_core/handlers/ratelimit_handler.py`) are LRU-bounded at 10,000 tracked IPs via the shared `_lru_pop_or_create` helper (`guard_core/_utils/lru_store.py`); every 429 response carries a `Retry-After` header set to the effective rate-limit window. `BehaviorTracker.usage_counts`/`return_patterns` (`guard_core/handlers/behavior_handler.py`) apply the same 10,000-client LRU bound per outer key (endpoint id, or `endpoint:pattern` for return-pattern rules).

### Detection

`detection_compiler_timeout` (default `2.0`, range `0.1`-`10.0`; per-pattern match timeout), `detection_max_content_length` (default `10000`), `detection_max_body_inspect_bytes` (default `262144`), `detection_max_scan_values` (default `512`, `ge=2`, `le=100_000`; caps the total query-parameter, header, JSON-key/value, form-field, and multipart-part values scanned per request, including JSON embedded in a single value; each named value costs two scan units, name and value, so `2` is the floor; once reached, remaining request values are not scanned and a one-time `logger.warning` names the client IP -- `guard_core/_security_config_fields.py`, `guard_core/_utils/detection_scan.py`), `detection_max_json_depth` (default `32`, `ge=1`, `le=1000`; caps how deep the structural JSON-body walk descends, an explicit-stack iteration with no recursion; a dict or list reached at this depth is serialized back to text and scanned as one value instead, bounded by `detection_max_content_length`, and a one-time `logger.warning` names the client IP -- GHSA-f6cf-jjhc-qp85, CWE-674, `guard_core/_security_config_fields.py`, `guard_core/_utils/body_content_scan.py`), `detection_preserve_attack_patterns` (default `True`), `detection_semantic_threshold` (default `0.7`), `detection_anomaly_threshold` (default `3.0`), `detection_slow_pattern_threshold` (default `0.1`), `detection_monitor_history_size` (default `1000`), `detection_max_tracked_patterns` (default `1000`), `detection_threat_score_threshold` (default `1.0`), `detection_scan_body` (default `True`), `enabled_detection_categories` (`frozenset[str]`, subset of the 19 categories; defaults to all 19), `enable_penetration_detection` (default `True`), `enable_dynamic_rules` (default `False`), `body_read_timeout` (default `3.0`, `gt=0.0`, `le=30.0`; seconds an adapter's `read_body_prefix`/`body` call is given before the body is treated as unavailable -- bounds the async tree via `asyncio.wait_for`, and in the sync tree bounds how long the caller joins the daemon thread the read runs on), `sync_body_read_max_concurrent` (default `64`, `ge=1`, `le=10000`; cap on daemon threads the sync tree may have blocked at once inside an adapter body read). See `docs/configuration/detection-tuning.md` in the guard-core repository for the full field-by-field tuning guide.

`PatternCompiler.validate_pattern_safety`'s own probe/wait budget (50ms cost-arbiter soft budget, 2.0s killable-subprocess hard timeout) is a hardcoded constant, not a `SecurityConfig` field; see [the detection reference](detection.md#redos-safety) for the mechanism.

### Redis

`enable_redis` (default `True`), `redis_url` (default `redis://localhost:6379`), `redis_prefix` (default `guard_core:`), `redis_socket_connect_timeout` (default `2.0`), `redis_socket_timeout` (default `2.0`), `redis_health_check_interval` (default `30`), `redis_max_connections`, `redis_retries` (default `1`; retries with exponential backoff before surfacing a transient Redis error), `redis_fail_open` (default `False`; on `GuardRedisError` from a per-request check, skip the failing check and fall through instead of honoring `fail_secure` -- `guard_core/core/checks/pipeline.py`).

`redis_fail_open` also governs startup, in `HandlerInitializer.initialize_redis_handlers` (`guard_core/core/initialization/handler_initializer.py`): if `RedisManager.initialize()` raises `GuardRedisError` because Redis is unreachable, `redis_fail_open=True` (not the default) degrades the process to the in-memory backends used when Redis is disabled -- for the lifetime of the process, it does not retry the Redis connection later -- while `redis_fail_open=False` (the default) re-raises `GuardRedisError` so the adapter's own startup handling sees a clean error instead of an unhandled exception.

`redis_fail_open` also governs the rate limiter's Redis path (`_redis_request_count` in `guard_core/handlers/ratelimit_handler.py`, both `check_rate_limit` and `check_rate_limit_by_ip`): a Redis failure there used to always fall back to the in-memory window regardless of the flag, silently turning the shared cross-worker limit into a per-process one. It now honors `redis_fail_open` like every other check -- `True` keeps the in-memory fallback and logs a `WARNING` once per process instead of an `ERROR` per request; `False` raises `GuardRedisError` so the pipeline's `fail_secure` handling (or, for `check_rate_limit_by_ip`, the caller's own handling) decides the outcome.

### Telemetry

`enable_agent`, `agent_api_key` (required when `enable_agent=True`), `agent_strict`, `agent_endpoint`, `agent_project_id`, `agent_buffer_size`, `agent_flush_interval`, `agent_status_interval`, `agent_enable_events`, `agent_enable_metrics`, `agent_timeout`, `agent_retry_attempts`, `agent_project_encryption_key`, `agent_guard_version`, `agent_high_watermark_ratio`, `agent_max_concurrent_flushes`, `agent_buffer_overflow_policy` (`Literal["drop", "block", "raise"] | None`, rejected at construction if set to anything else), `agent_backoff_factor`, `agent_sensitive_headers`, `agent_max_payload_size`, `agent_compression_enabled`, `agent_compression_threshold`, `agent_install_id`, `agent_payload_signing_secret`, `on_error` (also forwarded to `AgentConfig.on_error`, receiving guard-agent's `transport_send`/`encryption` failures alongside guard-core's own `agent_init`/`geoip` failures), `enable_enrichment` (requires `enable_agent=True`), `enable_otel`, `otel_service_name`, `otel_exporter_endpoint`, `otel_resource_attributes`, `enable_logfire`, `logfire_service_name`.

`to_agent_config()` builds an `AgentConfig` from the agent fields when `enable_agent=True` and `agent_api_key` is set, else returns `None`. The ten `agent_*` fields listed above with a `None` default (plus `on_error`) are each omitted from the `AgentConfig(...)` call when unset, so `AgentConfig`'s own default applies instead of a duplicated value drifting out of sync with guard-agent.

### Pipeline behavior

`passive_mode` (log only, no block), `fail_secure` (default `True`; block 500 on check exception vs continue), `enforce_https`, `security_headers` (dict: `enabled`, `hsts`, `csp`, `frame_options`, `content_type_options`, `xss_protection`, `referrer_policy`, `permissions_policy`, `custom` keys), `custom_request_check`, `auth_verifier` (default `None`; global default verifier for `require_auth`/`api_key_auth` routes with no per-route `verifier=`, contract `verifier(request, credential) -> Principal | None`, sync or async in async deployments, sync-only in WSGI), `custom_response_modifier`, `enable_cors`, `cors_allow_origins`, `cors_allow_methods`, `cors_allow_headers`, `cors_allow_credentials`, `cors_expose_headers`, `cors_max_age`, `exclude_paths`, `route_resolution_strict` (default `False`), `lazy_init` (default `True`), `emergency_mode`, `emergency_whitelist`.

Per-route gates -- `required_headers`, `blocked_user_agents`, `max_request_size`, `allowed_content_types`, `custom_validators`, `time_restrictions`, `require_referrer`, `auth_required`, `api_key_required` -- live on `RouteConfig`, set via decorators, not on `SecurityConfig`. `require_auth`/`api_key_auth` (`guard_core/decorators/authentication.py`) also accept a per-route `verifier=`; without a resolvable verifier (route-level or `auth_verifier`), the `authentication` check 401s every request on that route fail-closed (`guard_core/core/checks/implementations/authentication.py`). `require_authorization_header(scheme=...)` is a separate presence/scheme-only decorator, not authentication, and cannot be combined with `require_auth`/`api_key_auth` on the same route.

`security_headers["custom"]` header names are validated against the RFC 9110 token grammar (`SecurityHeadersConfigMixin._validate_header_name`, `guard_core/handlers/_security_headers_config.py`); an invalid name (CRLF or any other non-token character) raises `ValueError`. The same validation runs on a `custom_headers` entry loaded back from Redis (`SecurityHeadersCacheMixin._load_cached_config`, `guard_core/handlers/_security_headers_cache.py`); an entry that fails is discarded with a logged warning and the prior configuration is kept, rather than applying an invalid cached header.

### Logging

`custom_log_file`, `log_suspicious_level` (default `WARNING`), `log_request_level` (default `None`; set to enable request logging), `log_country_check_level` (default `INFO`; non-block country verdicts, `None` silences them), `log_format` (`"text"` or `"json"`), `custom_error_responses`.

### Mute sets

`muted_event_types`, `muted_metric_types`, `muted_check_logs`. Validated sets; unknown values raise `ValidationError` listing valid values. See the telemetry reference for the valid value lists.

## Optional extras

`import guard_core` no longer loads `aiohttp`, `maxminddb`, `redis`, `guard_agent`, or `cryptography`; those load lazily, only when a check that needs them is actually built or a feature that needs them is actually configured. Three optional-dependency extras package the split: `redis` (the `redis` package, needed when `enable_redis=True`), `cloud` (`aiohttp` and `requests`, needed when `block_cloud_providers` is set or `enable_dynamic_rules=True`, since dynamic rules can turn cloud blocking on at runtime), and `geo` (`maxminddb`, needed when `blocked_countries` or `whitelist_countries` is set and no custom `geo_ip_handler` is supplied, the one case where guard-core constructs its own `IPInfoManager`). All three extras' packages are also still listed in guard-core's base `dependencies` through the 3.x line, so an existing install is unaffected; the extras exist so a deployment can be explicit about which features it needs, and they become the only source of those packages at 4.0.

`SecurityConfig`'s `validate_optional_extras_installed` model validator checks `importlib.util.find_spec` (never a bare `import`) for each configured feature and raises `ValueError` naming the missing extra's `pip install guard-core[...]` command, instead of letting the feature fail later with a raw `ImportError`. Configuring a feature whose extra is not installed fails at `SecurityConfig` construction, not mid-request.

## Validation hooks

`validate_agent_config` raises `ValueError` if `enable_agent=True` but `agent_api_key` is missing. `enable_enrichment=True` without `enable_agent=True` raises `ValidationError`. Country-list conflicts emit a warning (not an error) when both `whitelist_countries` and `blocked_countries` are set. `SecurityConfig` still allows unknown constructor keyword arguments (`extra="ignore"`, unchanged); `warn_unknown_fields` logs a `guard_core.models` warning naming each one so a typo'd field name is not silently a no-op. `extra="forbid"` is the intended behavior at a future major release; this warning is the migration runway.

Three more construction-time `model_validator(mode="after")` hooks warn (not raise) on the `guard_core.models` logger: `warn_trusted_proxies_prefix_zero` fires when any `trusted_proxies` entry is a `/0` network (`0.0.0.0/0`, `::/0`), since every peer is then trusted to set `X-Forwarded-For`; `warn_whitelist_prefix_zero` fires when any `whitelist` entry is a `/0` network, since every address is then whitelisted and `blacklist`, `blocked_countries` and IP bans can never block anyone (precedence is unchanged, this is a signal only); `warn_empty_enabled_detection_categories` fires when `enabled_detection_categories` is empty while `enable_penetration_detection=True`, since detection is then enabled but can never match anything. All three are defined in `guard_core/_security_config_validators.py` (the shared `_is_prefix_zero_network_entry` helper backs the two `/0` checks) and wired into `SecurityConfig` in `guard_core/models.py`; none block construction.
